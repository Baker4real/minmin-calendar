# Minmin Calendar Context

## Domain Language

- **Room**: A private two-person sharing space identified by a six-character `roomCode`.
- **Launch screen / 启动首屏**: The screen the app opens on — the bind page. A successfully validated bound user is redirected straight to the 首页 tab, so the bind page rests only in unbound, needUnbind, or validation-failure states, with a minimal 进入应用 fallback when the home jump fails or right after room creation. The tab named 首页 is a different thing: that tab is the calendar page.
- **Room leave**: A server-side membership revoke flow that removes the current user from a Room while preserving the remaining member when present.
- **Archived room**: A room with no active members. Its `roomCode` and records are retained for explicit creator recovery, but normal record CRUD is closed until recovery.
- **Period record**: One shared menstrual-period record with a start date, a Period status, optional note, flow level, and symptom tags. A known date range that overlaps more than one calendar month is still one Period record, not one record per month.
- **Period status / 经期状态**: The record state is one of ongoing, ended with a known end date, or ended with an unknown end date. A missing end date is never treated as proof that the period lasted one day.
- **Ongoing period / 进行中经期**: A Period record whose start is known and whose end has not yet been recorded. Calendar projection covers the start date through Today, without inventing future dates, until the user completes the record.
- **Unknown-end period / 结束日期不详经期**: A Period record known to have ended when the exact end date is unavailable. Calendar projection shows only the known start date and does not infer duration.
- **Owning Period record / 归属记录**: The Period record used to describe a day covered by multiple Period projections. An Ongoing period takes precedence; otherwise the record with the latest start date owns the day. If several Ongoing periods cover it, the latest start wins. The period day count starts at the owning record's start date, inclusive. This is a display attribution; every record remains separate.
- **Period record count**: How many Period records the Room currently holds. It is not Period duration and not Days in viewed month. The homepage does not show this count.
- **Homepage status line / 首页状态行**: The single line under the month navigation. It says which day of the current period it is, how the next prediction stands (before the window, inside the window, or late), or that there is not enough data to predict. Tapping it opens the prediction explanation. It is not the Period record count and not the Monthly recap.
- **Period duration**: The inclusive day count of a Period record from a known `startDate` through a known `endDate`. A same-day start and end is a valid one-day duration; an Ongoing period or Unknown-end period has no exact duration and is excluded from duration averages until completed. This is a property of the record, not of a month view.
- **Monthly recap / 小结**: Homepage summary for one viewed calendar month. It lists Period records and Memory records that overlap that month. Its total period days count the union of projected dates covered in that month, once per date, rather than adding each record's Days in viewed month. It is not a second Period record.
- **Days in viewed month**: Inclusive day count of the intersection between one Period record's projection and the Monthly recap's calendar month. This per-record quantity is not Period duration and is not the month's union coverage count.
- **Memory record / happy time / 欢乐时光**: A dated note shown as a heart marker on the calendar. Several Memory records may share one date; each still counts as its own record. The user-facing name is 欢乐时光. 记忆, 特别日子, and 特别时刻 are retired.
- **Record names**: Entities are 经期 and 欢乐时光. Actions are 记经期, 记欢乐时光, 补记经期, 补记欢乐时光, 编辑这次经期, and 记结束.
- **Record author / 记录作者**: Whether the current member created a Period or Memory record. dataOp adds `createdByMe` on the client projection for list, add, and update, and omits the creator openid, room code, and created time. When the Room is paired, list rows and day detail say 我记的 or TA 记的. An unpaired Room does not show that label.
- **Memory month group / 欢乐时光月份分组**: The Memory records whose dates fall in one calendar month, presented together in the 记录 tab's 欢乐时光 segment. It is a view, not a record: each Memory record keeps its own date and calendar heart, and nothing is stored per month. Its count is the number of Memory records in that month, the same number the Monthly recap / 小结 reports for that month, but it is not the Monthly recap. Avoid 统合记录 or 月度记录, which suggest a stored per-month record.
- **Edit draft / 草稿**: Edit-form input stashed in local storage when the Period/Memory edit page is hidden or unloaded, restored with a 「已恢复上次未完成的输入」 notice on return, and cleared after a successful save. Drafts are keyed per record identity (new vs. each existing record) and never leak across records.
- **Calendar cell**: A homepage day tile that may show date number, lunar text, holiday/workday tag, and markers.
- **Overlap day / 重叠日**: A calendar day covered by both a Period record and the Prediction window. Projection sets `isPredict` false for that day, so the cell, day detail, and screen reader express period (and memory if present) only. The prediction window itself, the homepage status line, legend, and prediction explanation stay unchanged.
- **Prediction / 可能开始的日子**: The estimated next period start, derived from previous period gaps. The prediction window is that start date ± the fluctuation in days. Days inside it are 下次可能开始的日子 and may show 「预」, unless the day is an Overlap day. The homepage status line is how that estimate is phrased for today. Prediction is not a Period record and is not written back onto records.
- **未同步集合 / Unsynced collection**: A Period or Memory collection that has not yet supplied a complete successful list for the current Room. It may be empty or contain locally saved records; neither proves that the Room has no records. Existing bands, hearts, record details and recap highlights remain visible. Unsynced Periods supply no period day count, prediction or ongoing-completion reminder; their quick entry says 记结束 when a local Ongoing period exists, otherwise 记经期. Unsynced Memories change only the Memory part of the recap. Either unsynced collection keeps the recap entry instead of the first-record guide.
- **Today**: One date sampled for each Calendar projection, shared by the current-date highlight, status, quick entries, reminders, day titles and future-day actions; it should not reuse the memory heart marker.
- **Lunar date**: Chinese lunar calendar text such as `正月初一` or `冬月十六`.
- **Public holiday**: China official holiday range or adjusted workday label displayed in calendar cells.

## Product Principles

- Calendar markers must be semantically clear. A visual symbol should not mean two different things. On an Overlap day, only the period meaning is expressed; prediction is suppressed for that cell only.
- A Period record may be saved before its end is known. The form distinguishes Ongoing, Unknown-end, and completed records instead of using an empty end date to carry multiple meanings.
- Recorded dates cannot be in the future. The system does not write an end date the user has not confirmed, and it does not automatically close an Ongoing period. Completing an ongoing record shows today as the end date on the form before save; the user confirms that same record.
- Ongoing periods use the known start date for cycle prediction but do not contribute an exact duration. Unknown-end periods contribute neither an exact duration nor an inferred range.
- A Room has at most one Ongoing period record for the period stream; a second add action reopens the existing record. Overlapping completed records remain a separate, later data-quality concern and are not merged or hard-blocked by this rule.
- Flow and symptom allowed values stay light/normal/heavy and cramps/headache/tired/acne/mood/sleep/cravings. `utils/cycle.js` owns labels; `cloudfunctions/dataOp/roomRecords.js` keeps a self-contained copy for standalone deploy. Tests lock both allowed-value sets equal; do not invent a shared runtime module for this small list.
- Monthly recap copy must not use unlabeled 「天」 for both Period duration and Days in viewed month. Any viewed month that does not fully contain a Period record states both quantities on that record. The period range shows that the same record continues across months, including the start month and year boundaries, so the recap does not also say 「从上月延续」 or 「本月开始」. Period duration and Days in viewed month are stated per Period record; the month total counts the union of covered dates, never the sum of the per-record quantities. A memory count is not repeated as 「特别日子」.
- Shared data must stay room-scoped and private.
- The app should feel soft and personal, but not at the expense of readability. Color, type size, and calendar-cell treatment live in `DESIGN.md`; this file owns marker meaning.
- Date behavior should be tested before UI code relies on it.

## Technical Shape

- `app.js` initializes WeChat Cloud with the active environment.
- `utils/cloud.js` wraps frontend calls to `cloudfunctions/dataOp/index.js`; `RoomDataClient` is the sole frontend records access interface for room-scoped reads/writes.
- `utils/roomResolver.js` owns cached-or-fresh active-room resolution for `RoomDataClient`; it does not execute stale-room repair or access records directly.
- `utils/roomRecordsSnapshot.js` consumes only `RoomDataClient` and returns room-scoped `periods` + `memories` outcomes in a collection-keyed `collections` map. Home reads both lists together and allows retryable partial success; Settings export reads sequentially, stops at the first failure, and requires both lists before writing a backup.
- `utils/roomAccessOutcome.js` owns client-side classification of structured and legacy room access failures and the sole failure presentation mapping for list, save, delete, export, and homepage loading. It decides the Room repair branch and whether to retry directly or check the record first; `utils/wxPrompts.js` executes its modal, toast, inline, retry, and binding actions. Settings room-code display state stays here.
- `utils/recordCommands.js` owns both Period and Memory record-edit sessions under [ADR-0008](docs/adr/0008-home-record-sync-and-record-edit-ownership.md): given kind, route and a render callback, each session holds complete form fields, field errors, saving/deleting/submitted state and the draft-restored flag, and coordinates field changes, identity-scoped drafts, validation, RoomDataClient saves, unconfirmed-write read-back, delete confirmation, success notification and delayed return. The Period configuration also owns status transitions, history-backed duration hints, flow/symptom labels, overlap choices through `periodCoverage`, and replacing form identity, draft key and baseline with the actual reopened record. Both edit pages render session output and forward form/lifecycle events; the record-tab list-loading interface stays in this module. Room failures use `roomAccessOutcome` and `wxPrompts`.
- `utils/recordPageSync.js` owns saved/deleted record change construction (merged records count as updates), optional notifications to the previous homepage or record-tab adapter, and the single declaration, writing and one-time consumption of the record-tab segment intent key. Edit sessions and the compatibility Memory route use this owner; pages do not declare the storage key.
- `utils/roomRecordsSync.js` owns homepage records and synchronization under [ADR-0008](docs/adr/0008-home-record-sync-and-record-edit-ownership.md): per-collection revisions, complete-list synchronization and pending local confirmation, one in-flight Promise shared by foreground/background callers, local add/update/remove reconciliation, partial failures and named retry copy, and sync-pill state/text. Serial loads cannot overtake each other; a local change during loading invalidates only that collection's snapshot and keeps it pending until a later load. It directly reads through RoomDataClient and publishes adopted collection results as one calendar update. Blocked Room outcomes go to `roomAccessOutcome` and `wxPrompts` for Home presentation. The homepage Page triggers loads from show/pull/retry, forwards `recordPageSync` changes, projects the module's records/sync state once per calendar update, and keeps the pill display lifecycle/auto-hide timer; rendering does not store records.
- `utils/settingsFlow.js` owns room-code copy, all-or-nothing data export, local-cache helper flows, and the shared Room leave confirmation → server call → outcome flow used by Settings and Bind. Export failures use `roomAccessOutcome` and `wxPrompts`; the shared leave flow owns the one-time notice key, writes the notice after Settings leave succeeds, and consumes it when Bind is shown. Notice storage stays best-effort so verification and navigation can continue; pages render outcomes and handle navigation.
- `utils/homeCalendarState.js` owns the pure Calendar projection and is the single source of homepage calendar content: bands, hearts, prediction markers and explanation, status, quick-entry labels/ARIA/destinations, ongoing-completion candidates and cycle reminders, each day's title/subtitle/future notice/actions, monthly recap and its entry versus the first-record guide, back-to-today visibility, legend definitions and record-success feedback. It alone interprets Unsynced collections. The Page samples Today once per projection and renders the result; it only filters reminder candidates through local seen storage and marks them seen after a visible render followed by leaving, or after a tap. Period bands use `periodCoverage`'s monthly union; day counts and status words use the same Owning Period record, record-detail ranges ask its projection question, and new Period destinations ask its entry question. Day detail keeps every covered record separately. Record feedback lights only the confirmed new/completed record's cells in the viewed month.
- `utils/recordEditRoute.js` owns Period record and Memory record edit URL construction plus edit-page route option hydration, including the Memory date ceiling at today. Period status comes from `periodCoverage`; the route owns new-form date defaults and the explicit completion intent.
- `utils/recordDraft.js` owns edit-form draft save/restore/clear as pure functions keyed per record identity; `createWxDraftStorage` is the only wx local-storage seam.
- `utils/room.js` owns room-code cache, recovery, create/join, local clear, and server-side leave calls. Create/join failures include a structured reason (`already-in-other-room` from existing server code -5, otherwise `other-failure`) alongside filtered display copy; Bind uses the reason to offer leave. Leave clears the local Room cache only after server success.
- `utils/util.js` owns date formatting, lunar conversion, official holiday metadata, base calendar-grid construction, and the month-swipe decision (`decideMonthSwipe`).
- `utils/periodCoverage.js` owns period status, projection ranges, the Owning Period record and inclusive day count for a date, monthly coverage dates/count as a union, and new-period entry destinations with the shared ongoing notice. Homepage entries, record tab entry and the edit-page overlap choice ask it; it performs no record writes, merges or hard blocks.
- `utils/cycle.js` owns cycle prediction, reminder derivation, Period duration from dates (`getPeriodDuration`), flow labels, symptom labels, and the display grouping metadata (身体 / 情绪与睡眠). It asks `periodCoverage` for period status, projection, day attribution and ongoing entry selection; existing cycle accessors delegate to that owner. Allowed symptom values stay the same set as the cloud copy.
- `utils/calendarInsights.js` owns prediction explanation and monthly recap copy from supplied records; Calendar projection supplies the homepage's unsynced presentation. Month totals use `periodCoverage`'s coverage count; each record retains its own Days in viewed month and Period duration.
- `pages/index/homepageSheets.js` is Home's sole sheet registry. Its row order owns system-back priority: information → month picker → tools menu → day actions. Each registered name derives its Visible/Mounted/Phase keys (and Handoff for information), WXS drag identity and reset token; the same close action serves buttons, drag and system back. The registry creates the four lifecycles and their page-obscuring configuration, preserves prediction-close emphasis, and clears content only after unmount. The Page forwards sheet events and supplies content; lifecycle leave commits visibility and the leaving pose together. Tools use `toolsMenu*`, day actions use `dayActions*`, and information uses `infoSheet*` throughout the lifecycle bindings.
- `utils/sheetLifecycle.js` owns shared two-render entry, timed exit and reversal, atomic handoff, page-obscuring decoration, native tabBar visibility/recovery, system-back interception/re-entry and reduced-motion probing. It has no homepage sheet names or key lists; Home derives its configuration from its registry. The Settings help-sheet adapter and the homepage sync pill continue to use these mechanisms.
- `utils/safeArea.js` owns runtime safe-area computation for status-bar top, gesture-area bottom, the capsule rectangle, nav-bar height, and the inset that clears the capsule; page roots inject `--safe-top`, `--safe-bottom`, `--nav-bar-height`, and `--capsule-right`.
- `cloudfunctions/dataOp/index.js` is the cloud runtime adapter for room-authorized CRUD on `periods` and `memories`.
- `cloudfunctions/dataOp/dataOpHandler.js` owns active-room membership lookup and rejects archived rooms before record dispatch.
- `cloudfunctions/dataOp/roomRecords.js` returns one client record projection from list, add, and update: the record fields plus `createdByMe` when the caller is known. The projection omits the creator openid, room code, and created time. Add and update still return that projection for optimistic homepage synchronization.
- `cloudfunctions/_shared/roomMembershipLifecycle.js` is the canonical source for Room membership creation, lookup, join, leave, ownership transfer, archive, and recovery transactions.
- `cloudfunctions/createRoom|joinRoom|getMyRoom|leaveRoom/index.js` are self-contained deployment adapters; each loads a byte-identical local `roomMembershipLifecycle.js` artifact generated by the deterministic `_shared/syncRoomMembershipLifecycle.js` assembly script.

## Room Lifecycle Boundary

- Active room access is authorized through `rooms.createdBy` / `rooms.partnerOpenid`; `roomMembers` is a concurrency lock, not the record authorization source.
- `rooms` must retain `roomCode_1_unique` plus the non-unique `createdBy_1_status_1` and `partnerOpenid_1_status_1` indexes. The composite indexes support Room identity lookup performance only; they do not change authorization semantics or make `roomMembers` an authorization source.
- Last-member leave archives the room instead of deleting it. Archived rooms reserve their original `roomCode`, are not returned by `getMyRoom`, cannot be joined directly, and cannot access records through `dataOp`.
- The original creator can recover an archived room by creating again. Recovery keeps the same `roomCode`, so existing `periods` and `memories` become accessible without migration.
- Homepage loading may show partial `periods` / `memories` data when one collection has a retryable failure, but Settings export still requires both collections to load successfully.

## Holiday Data Boundary

- `utils/chinaHolidays.js` currently contains official China holiday and adjusted-workday ranges for 2001-2026.
- Years inside that published range may show official off-day and adjusted-workday facts from the data table.
- Years beyond 2026 may still show static festival names such as Spring Festival, Qingming, Labor Day, Dragon Boat Festival, Mid-Autumn Festival, National Day, and New Year's Day, but must not infer adjusted workdays.
- Before the app enters a year beyond `PUBLISHED_HOLIDAY_END_YEAR`, update the published ranges from State Council holiday notices and keep the maintenance test green.

## Verification Baseline

After date, room, calendar, or page behavior changes, run the command set in `README.md` Verification. Expand test and source paths to absolute paths when the shell cannot resolve relatives.

Manual WeChat DevTools verification is still needed for layout and end-to-end room flow behavior.
