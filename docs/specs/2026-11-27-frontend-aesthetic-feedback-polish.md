# 前端审美与反馈精修

**Issue:** [#276](https://github.com/Baker4real/minmin-calendar/issues/276)

## Problem Statement

敏敏子日历已经具备明确的 Aurora Bloom 视觉身份、稳定的 Room 数据流、完整的日历语义和较成熟的无障碍护栏。2026-11-26 基于十二个设计参考入口、当前源码、设计规范、静态护栏和十五张当前版本替身 Room 截图的审计确认：现有深海军、暖玫瑰、浅粉、柔金与薰衣草配色适合双人私密日历，不需要换色或重做。

剩余问题主要是内容权重与构图：首页状态行没有充分突出“现在是什么情况”；经期月份分组与设置页的同权重容器分散了对记录事实和房间凭证的注意；欢乐时光编辑页在高屏上没有把留白转化为书写空间；日历图例存在重复卡片层级；使用说明的主题标题弱于正文；配对后的首页缺少持续的双人共享标识。另有三个反馈缺口：本月小结复制失败没有提示，已有记录未修改也会产生保存流程与成功反馈，日历密度写入失败会让可见选择与后续恢复值不一致。折叠分组在大数据量下的渲染成本已有结构线索，但尚未形成性能结论。

## Solution

在不改变 Aurora Bloom 色板、记录语义、Room 权限、共享弹层家族和双密度日历的前提下，完成一组克制的内容层级与反馈精修：

- 首页状态行保留原文案、几何和读屏名称，以暖白和字重突出天数、预计日期、可能开始窗口、晚于预测的天数及上次开始日期。
- 经期记录列表提高日期范围的视觉权重，降低经期月份分组容器的装饰权重；设置页仅让房间凭证保留高级玻璃卡，其余设置组使用安静表面。
- 欢乐时光编辑页让空内容书写区在高屏延展到固定保存区上方，短屏保留原有最小高度，长文继续自动增高。
- 日历图例去掉整行重复卡片，保留样本格与全部标记语义；使用说明提高主题标题层级并增大主题间距。
- 首页共享顶栏在已配对 Room 中显示由现有品牌图形派生的静态双心标记，标题仍按安全区账本居中，同步胶囊出现时继续替换整个标题槽。
- 本月小结复制失败显示明确错误提示；已有记录未修改时保存只清理对应草稿并返回，不写云、不震动、不提示保存成功、不发布记录变化；日历密度写入失败恢复原选择并提示。
- 使用 500 与 1000 条构造记录测量折叠分组的渲染成本，并按本规格的量化判定规则决定是否引入懒挂载。
- 将欢乐时光文本域和共享弹层关闭按钮的读屏名称改为具体用途名称。

## User Stories

1. 作为打开首页的用户，我希望经期第几天比状态行其他文字更容易被看到，以便立即理解当前情况。
2. 作为查看下次预测的用户，我希望预计开始日期在状态行中有明确强调，以便不用逐字寻找关键日期。
3. 作为处于预测窗口内的用户，我希望“这几天可能开始”成为状态行的视觉重点，以便快速判断当前窗口意义。
4. 作为预测窗口已经过去的用户，我希望晚于预测的天数或上次开始日期得到克制强调，以便理解当前状态并采取下一步。
5. 作为使用读屏的用户，我希望状态行视觉强调不改变原有朗读顺序和完整名称，以便获得与视觉用户相同的信息。
6. 作为查看最长状态文案的用户，我希望强调后月份导航、倒数和箭头仍保持原有单行几何，以便页面不跳动、不截断。
7. 作为浏览经期记录的用户，我希望日期范围比月份容器更容易扫读，以便快速找到某一次经期。
8. 作为查看经量和症状的用户，我希望提高日期权重不会压制经量、症状、作者和时长信息，以便完整理解一条记录。
9. 作为折叠经期月份分组的用户，我希望材质降噪不改变展开状态、触控热区和折叠动效，以便继续熟练使用列表。
10. 作为查看设置页的用户，我希望房间凭证比普通设置组更突出，以便立即找到双人 Room 的核心信息。
11. 作为调整日历显示或导出数据的用户，我希望安静表面仍保留清楚的分组、分隔线和按压反馈，以便完成任务而不受装饰干扰。
12. 作为在高屏设备上新增欢乐时光的用户，我希望书写区自然延展到保存区上方，以便页面像一张完整信笺而不是短备注表单。
13. 作为在短屏设备上书写欢乐时光的用户，我希望文本域仍有可用的最小高度并能滚动查看，以便内容不被保存区遮挡。
14. 作为输入长文的用户，我希望文本域继续自动增高且字数提示、草稿和固定保存行为不变，以便顺畅完成书写。
15. 作为使用读屏书写欢乐时光的用户，我希望文本域名称明确为欢乐时光内容，以便区分其用途。
16. 作为第一次打开日历图例的用户，我希望沿“符号到含义”连续纵向扫读，以便快速理解今天、经期、欢乐时光、预测、节日和调休。
17. 作为查看图例样本的用户，我希望减少整行卡片后样本颜色、色带、胶囊和文字仍保持原样，以便图例与日历继续一致。
18. 作为打开使用说明寻找答案的用户，我希望四个主题标题不低于正文视觉层级，以便先定位主题再阅读段落。
19. 作为阅读较长使用说明的用户，我希望固定标题、关闭按钮和内部滚动行为保持不变，以便专注阅读。
20. 作为已配对 Room 的成员，我希望首页标题旁有轻量双人共享标记，以便主流程持续表达这是一本共同日历。
21. 作为未配对或正在等待对方加入的用户，我希望双人共享标记只在已配对状态出现，以便界面不误解 Room 状态。
22. 作为看到同步状态的用户，我希望同步胶囊继续按现有生命周期替换标题槽，以便共享标记不会与同步文案争抢空间。
23. 作为复制本月小结的用户，我希望剪贴板失败时看到明确提示，以便不会误以为已经复制成功。
24. 作为打开已有记录但未作修改的用户，我希望点保存后直接返回，以便不等待无意义的云端请求。
25. 作为未修改保存的用户，我希望没有保存成功提示、震动或新增记录反馈，以便系统反馈真实表达发生的行为。
26. 作为恢复过草稿又改回原值的用户，我希望未修改保存清理对应草稿，以便下次不会看到过期恢复提示。
27. 作为修改了任意字段的用户，我希望正常保存、校验、合并、失败恢复和记录发布逻辑完全保留，以便真实修改可靠写入。
28. 作为切换日历密度的用户，我希望本地写入失败时看到提示并恢复原选择，以便界面不承诺无法持久化的偏好。
29. 作为本地存储正常的用户，我希望日历密度切换仍立即生效且不增加提示，以便保持当前轻量操作。
30. 作为拥有多年记录的用户，我希望记录页在大量数据下仍能及时打开和切换分段，以便历史记录增长不会拖慢日常使用。
31. 作为使用减弱动效的用户，我希望本轮视觉调整不新增持续动画或空间位移，以便保持可预测的操作体验。
32. 作为喜爱现有 Aurora Bloom 的用户，我希望所有精修保留现有色板、双密度日历、弹层暗场和主次按钮关系，以便产品仍然熟悉且有自己的身份。

## Implementation Decisions

1. 色板保持不变。深海军继续作为画布，暖玫瑰只服务主操作、经期和既有强调，浅粉服务欢乐时光，柔金服务预测与节日，薰衣草服务辅助光与过渡；不增加新强调色或正文专用玫瑰色。
2. 首页状态句的现有文案所有者同时输出有序视觉分段和原始完整文本。所有分段拼接必须与原始文本逐字相同，首页 Calendar projection 继续提供唯一完整读屏名称。
3. 经期中强调“经期第 N 天”；超过预期时长时只强调主句，补充的超出天数保持次要。预测窗口前强调预计日期；窗口内强调“这几天可能开始”；窗口后第一至第七天强调“比预计晚 N 天”；第八天起强调上次开始日期，补记提示保持次要。记录不足和未同步状态不新增强调色。
4. 状态行强调使用现有中性强调白和标题字重，不增大 32rpx 字号、不改变 88rpx 行高、不增加卡片或图标。右侧倒数、箭头和全部最长文案继续服从现有宽度账本。
5. 经期记录日期范围使用现有控件字重和中性强调白。年份保持当前层级，不额外提亮；月份分组保留折叠、展开和记录归属逻辑。
6. 经期月份分组与设置普通组使用语义化的安静卡片修饰，取消装饰性棱镜顶线并降低表面权重，但保留既有圆角、间距、触控、分隔和按压契约。全局高级卡片样式保持不变。
7. 设置页房间组继续使用高级卡片；日历显示、数据和关于组使用安静卡片。危险区继续保持独立警示红形态。
8. 欢乐时光编辑页增加一个纯几何计算入口，根据实际视口高度、现有顶栏高度、底部安全区、表单抬头和固定保存区的已知槽位计算空内容文本域最小高度；结果不得低于 280rpx 对应的实际像素高度。
9. 欢乐时光文本域只在可用空间大于原最小高度时扩展，长文仍由现有自动增高机制接管。键盘、草稿、作者、日期面板、删除和固定保存区行为不变，不引入新的全局日历几何所有者。
10. 日历图例整行不再使用带填充和描边的卡片，采用组间留白与必要的细分隔。样本格继续复用日历格类，所有符号、颜色和读屏文本不变。
11. 使用说明主题标题使用正文尺寸与控件字重，正文保持现有正文角色；增加主题间距并降低主题容器装饰，不增加手风琴、搜索或额外导航。
12. 首页共享顶栏仅在 Room 已配对时显示静态双心标记。标记从现有内联品牌图形派生，不发起网络请求、不使用文本心形、不新增持续动画。
13. 双心标记与标题作为一个整体参与现有安全区居中账本。未配对、等待、未知和未绑定状态不显示；同步胶囊挂载时整个标题组让位，卸载后恢复。
14. 本月小结复制沿用现有剪贴板入口，成功提示不变，失败显示“复制失败”，且失败路径不显示成功提示。
15. 已有记录的未修改判断在编辑会话中完成，比较规范化后的草稿字段与当前记录基线；症状等多值字段按语义集合比较，不因数组顺序差异产生伪修改。
16. 未修改保存只适用于已有记录。新建记录、带完成经期意图的表单和任何真实字段修改继续走现有校验与云端流程。
17. 未修改保存清理该记录身份的草稿、停止后续草稿持久化并返回上一页；不调用云端更新、不显示保存成功、不触发轻触感、不发布记录变化，也不触发首页记录反馈。
18. 日历密度切换先保留当前值作为回滚点，写入失败后恢复该值并显示“保存失败，请重试”；写入成功路径不增加提示。读取失败继续使用现有默认密度，不新增进入设置页时的打扰。
19. 欢乐时光文本域读屏名称改为“欢乐时光内容”；共享弹层关闭按钮读屏名称包含当前面板名称，例如“关闭日历图例”。可见文案与面板结构不变。
20. 大数据量判定使用同一当前模拟器、同一替身 Room、相同构造记录和相同编译版本。500 与 1000 条记录都覆盖不少于二十四个欢乐时光月份分组，并包含足量经期月份分组。
21. 每种规模各执行五次首页进入记录 tab 的就绪测量和十次分段切换测量，取中位数。1000 条记录的就绪中位数超过 1500ms，或分段切换中位数超过 300ms，即实施折叠分组懒挂载；两项都未超过时保留现有始终挂载结构，并提交测量脚本与结果。
22. 懒挂载触发后，折叠分组首次展开时挂载记录行，已展开过的分组在本页生命周期内保留；收起继续隔离读屏与点按，并保留 0fr/1fr 过渡。测量未触发时不引入该结构变化。
23. 所有页面继续遵守共享模板与共享样式复用决定，不引入 UI 组件库、自定义组件、React 运行时或新渲染引擎。
24. 设计规范、动效与交互规范、领域上下文和验证日志同步反映最终行为；规格仓库副本保留拆分记录，父 Issue 正文保持发布时的规格事实源。

## Testing Decisions

1. 测试以外部可观察行为为主，优先复用现有纯 projection、页面 harness、编辑会话测试、设计护栏和替身 Room 运行入口。
2. 首页状态句在周期领域函数与首页 Calendar projection 两层验证：逐状态检查完整文本、强调分段拼接、倒数和读屏名称，并用页面 harness 验证实际渲染。
3. 首页最长文案继续走现有窄屏几何测试；新增断言证明视觉分段不会增加原始文本宽度、不会改变状态行高度或读屏内容。
4. 经期记录与设置页使用页面 harness 验证分组、展开、作者、时长、经量、症状、房间状态和全部操作不变；设计护栏只钉对比度、触控、共享材质和语义不变量。
5. 欢乐时光几何使用纯函数表格覆盖高屏、短屏、安全区和可用空间不足，再由页面 harness 验证文本域、固定保存区、草稿、日期面板和长文行为。
6. 图例与使用说明使用共享模板展开后的结构测试，确保样本复用、读屏顺序、固定 chrome 和内部滚动不退化。
7. 双人共享标记通过首页与共享顶栏 harness 覆盖未绑定、等待、已配对、未知和同步胶囊生命周期，并进入现有 320/375/390/430 坐标与标题居中检查。
8. 本月小结复制测试同时覆盖成功和失败，失败时断言剪贴板错误提示且没有成功提示。
9. 未修改保存在编辑会话 seam 覆盖两种记录、草稿恢复后改回原值、多值字段重排、真实修改、新建和完成经期意图；通过替身客户端调用记录证明无云端写入与无记录发布。
10. 日历密度通过设置页测试覆盖写入成功、写入失败回滚、重复选择、返回首页和再次进入设置页。
11. 读屏名称继续使用交互语义护栏，具体名称与可见面板用途同源。
12. 性能判定脚本保存有界汇总，包括记录规模、分组数、每次测量、两个中位数、源码指纹和最终分支；不用单张截图或主观体感替代测量。
13. 触发懒挂载时，补充首次展开、再次展开、收起隔离、保存后落点和记录删除后的行为测试；未触发时只保留测量与当前结构回归。
14. 视觉验收在当前微信开发者工具模拟器上使用替身 Room，覆盖首页两档密度、经期与欢乐时光记录、两个编辑器、设置、图例、使用说明和已配对标题；采集必须绑定当前源码和编译挑战。
15. 最终运行 README 规定的完整轻量检查组合、资源一致性检查、当前模拟器 UI 收尾清单和 git diff 检查。物理真机、系统读屏实听、真实惯性与系统减弱动效开关继续按既有验证边界披露。

## Out of Scope

- 不更换 Aurora Bloom 色板，不新增浅色主题、第二套强调色、正文专用玫瑰色或新的外部字体。
- 不删除全局面极光、玻璃、圆角、弹层暗场或全部棱镜顶线；降噪只发生在本规格列出的重复容器。
- 不改变完整与清爽两种日历密度，不缩小日历微字，不改变日历标记含义。
- 不削弱弹层遮罩，不填占绑定页留白，不把预测说明改成 AI 对话或医疗建议。
- 不改变记录 schema、云函数接口、Room 权限、记录作者规则、预测算法和日期领域规则。
- 不引入复杂筛选、搜索、权限矩阵、营销 Hero、贴纸、插画或新的常驻动画。
- 不引入 UI 组件库、自定义组件、React 依赖或 Skyline，不改变共享底部弹层家族。
- 不做多机型或物理真机兼容矩阵；当前模拟器之外的验证继续按维护者既有决定披露。
