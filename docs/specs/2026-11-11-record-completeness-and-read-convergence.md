# 记录取全、云端对齐与读取收敛

**Issue:** [#189](https://github.com/Baker4real/minmin-calendar/issues/189)

## Problem Statement

两位房间成员把经期和欢乐时光记在同一个 Room 里，指望记下的记录一条不少、两个人看到同一份、打开和切换页面不用多等。2026-11-11 对代码、文档、提交历史和本地门禁日志的复审发现，这三点各有缺口；另有两项维护成本会拖慢之后的改动。

### 目标与已确认选择

- 任何一类记录超过 100 条时，首页、记录 tab、保存后的核对和导出仍拿到该 Room 的全部记录。
- 仓库里的云端记录契约与真实云端一致，并在真实小程序上下文里核对过一次，结果有记录可查。
- 首页和记录 tab 显示时不再为配对状态单独请求一次；从首页记一条经期再回到首页，云函数调用从 6 次降到 3 次。
- 首页、记录 tab 和两个编辑页读同一份 Room 记录；切到记录 tab 时，已经读到的记录立即可见。
- 纯视觉调整不再需要改写只钉字面量的测试断言；没有调用者的代码和重复维护的模块清单各自收掉。

按复审建议已定的四个选择：

1. 首页仍分别读取两类记录，保留「一类读取失败时另一类照常显示」。把两类记录合并成一次读取不在本次范围。
2. 「手动常用周期」和「手动常用经期天数」两个分支自 2026-09-30 起没有生产入口，本次删除，不做设置入口。
3. Room 成员生命周期里没有调用者的函数留到下一次 Room 云函数部署时再删，本次不改，保持仓库与已部署产物一致。
4. 样式与标记护栏只保留不变量。本次处理已有断言被改写最多的三组（calendar-display、interaction-semantics、motion-performance），其余按同一条规则随改随删。

### 已知事实与约束

- 云端 `list` 没有指定条数，也没有分页。仓库锁定的云数据库 SDK 在未指定条数时固定取 100 条，指定时单次不超过 1000 条（已在本地安装的 SDK 源码中核实）。客户端把一次成功的列表当作完整集合，导出确认框写着「会导出全部经期和欢乐时光」。测试里的替身数据库没有这个默认上限，所以现有测试测不到截断。
- 列表按日期倒序，超出后最早的记录会同时从首页、记录 tab 和导出文件里消失，没有提示。保存结果未确认时的核对也读这份列表：被编辑的记录排在 100 条之后时，核对找不到它，用户会被告知「没有保存成功」。
- 验证记录在 2026-09-30 和 2026-10-10 两次写明 dataOp 的新契约尚未部署，之后没有部署记录。此后各 epic 的运行态验收用的是替身房间和替身云应答。真实云端当前运行的 dataOp 版本和两类记录的条数，从仓库读不到。
- 2026-09-30 之前的 dataOp 字段白名单里没有经期状态，记录作者是 2026-10-10 才加进云端应答的。线上如果还是更早的版本，经期三态或记录作者在真实云端不成立。
- 首页每次显示发两次 `list`，再调一次 `getMyRoom`，后者只用来取配对状态。dataOp 每次鉴权已经读过 Room 文档，其中就有配对状态。
- 记录 tab 每次显示发一次 `list` 和一次 `getMyRoom`；列表先渲染，等配对状态回来再渲染一次补上记录作者。
- 经期编辑会话打开时读一次经期列表，新建保存前再读一次，用来给时长提示和「这一天已有经期」的提示。
- 进行中经期的唯一性由云端写入路径保证；保存前的提示只是提醒，多条经期记录覆盖同一天仍然允许。
- ADR-0005：RoomDataClient 是前端读写记录的唯一 interface。ADR-0007：经期三态与预测样本规则。ADR-0008：首页记录同步归 `roomRecordsSync`，记录编辑归 `recordCommands` 会话，记录 tab 的列表加载入口留在 `recordCommands`。
- 云函数由维护者在微信开发者工具里部署；仓库里的工具不部署云函数。部署改变外部状态，执行前要维护者当次明确同意。
- 仓库和 issue 是公开的。真实日期、备注、条数、房间码和成员信息不进仓库、不进 issue。
- 样式与标记护栏的现状：14 个测试文件、约 9,500 行靠读 WXSS、WXML 和设计文档的文本做断言。124 次改动 WXSS 或 WXML 的提交里，103 次同时改了其中至少一个文件：53 次删除或改写了已有的断言行，另外 50 次没有动已有断言。被删除或改写的断言行最多的是 interaction-semantics、calendar-display、motion-performance（67、57、57 行）。整套 1,154 项测试约 6 秒跑完，成本在维护，不在速度。

### 关键失效方式

1. 分页排序不是全序，日期相同的记录在两页之间重复或漏掉；或者某一页失败后把已取到的部分当作完整列表返回。
2. 替身数据库继续没有默认条数上限，分页回退后测试照样通过。
3. 新 dataOp 部署后，已经在用的旧版小程序读写出错；或云端回滚后，新客户端因缺少新字段而报错。
4. 真实云端核对时写入的替身记录留在两个人的日历里，或核对证据把真实记录带进公开仓库。
5. 共用一份记录后，Room leave、加入另一个 Room 或 Room 修复之后还显示上一个 Room 的记录。
6. 多个页面订阅同一份记录，一次失败弹出多个提示，或隐藏的页面弹出提示。
7. 重构时丢掉「本地改动使在途快照失效」的规则，旧快照覆盖刚保存的记录。
8. 编辑会话不再读最新列表后，漏掉另一位成员刚记的进行中经期。这一条必须继续由云端的唯一性约束兜住。
9. 护栏瘦身时删掉了真正的不变量（对比度下限、减弱动效覆盖、触控目标下限），或把钉字面量的断言换个名字留下。
10. 删除「没有调用者」的代码前没有检索，删掉了测试之外仍可达的入口；或顺手改了 Room 生命周期源文件，让四份部署产物与已部署版本不一致。

## Solution

**记录取全。** 云端 `list` 成功就代表该 Room 该集合的全部记录。记录再多，首页的旧月份、记录 tab 的列表、保存后的核对和导出文件都完整；读取中途失败时用户看到的是失败和重试，不是一份悄悄变短的列表。

**云端对齐。** dataOp 部署一次，包含上面的取全和下面的配对状态。部署前记下线上现状，部署后在真实小程序里把进行中经期、欢乐时光、列表条数和导出各走一遍，结果写进验证记录。之后「云端是哪一版」有据可查。

**配对状态随列表返回。** 首页和记录 tab 第一次渲染就带上「我记的 / TA 记的」，不再多等一次请求、不再补渲染一次。

**一份 Room 记录。** 首页读到的记录，记录 tab 和编辑页直接用。切到记录 tab 立即看到列表，后台刷新后自动更新；打开编辑页不用再等历史读取；在任一页面保存后，其他页面已经是新的。换了 Room，上一个 Room 的记录一条不留。

**护栏只留不变量。** 改一个间距、时长或色值，只要没有越过设计规则的下限，测试保持通过；越过了才变红。

**收掉确定无用的部分。** 无人可达的预测分支、没有调用者的导出和重复的模块清单删除。

云函数调用次数（已绑定、本机已有房间码）：

| 场景 | 现在 | 完成后 |
|---|---|---|
| 首页显示 | 2 次 list + 1 次 getMyRoom | 2 次 list |
| 记录 tab 显示 | 1 次 list + 1 次 getMyRoom，应答到达后才有列表 | 2 次 list（静默刷新），已读到的记录先显示 |
| 打开经期编辑页 | 1 次 list | 0 次（经期已同步时） |
| 保存一条新经期 | 1 次 list + 1 次 add | 1 次 add |
| 从首页记一条经期并回到首页，合计 | 6 次 | 3 次 |

## User Stories

1. 作为房间成员，我希望欢乐时光超过 100 条后翻回旧月份仍看到当时的爱心，以便早期的记录不会无声消失。
2. 作为房间成员，我希望经期记录超过 100 条后旧月份的色带仍在，以便完整回看历史。
3. 作为房间成员，我希望记录 tab 列出该 Room 的全部记录，以便能找到并编辑任何一条。
4. 作为房间成员，我希望导出文件包含全部经期和欢乐时光，以便备份与确认框里的说法一致。
5. 作为房间成员，我希望编辑一条很早的记录后，即使保存结果一时未确认，核对也能找到它，以便不会被误告知「没有保存成功」。
6. 作为房间成员，我希望列表读取中途失败时看到失败和重试，以便不会把一份不完整的列表当成全部。
7. 作为房间成员，我希望每条记录在列表里只出现一次，以便不会误以为记了两次。
8. 作为还在用旧版小程序的房间成员，我希望云端更新后照常读取和保存，以便不必为了继续使用而立刻更新。
9. 作为维护者，我希望知道真实云端运行的 dataOp 对应仓库的哪个提交，以便判断线上行为是否与代码一致。
10. 作为维护者，我希望部署前留下旧产物和两类记录的条数，以便出问题时能回滚并核对数据没有变化。
11. 作为维护者，我希望在真实小程序里走一遍「新增进行中经期、再次新增被重开、补结束日、删除」，以便确认三态契约在真实云端成立。
12. 作为维护者，我希望确认真实云端拒绝未来日期的欢乐时光，以便该规则不只存在于本地测试。
13. 作为维护者，我希望列表返回的条数与云数据库里的计数一致，以便确认没有截断。
14. 作为维护者，我希望核对用的替身记录在结束时全部删除并回读确认，以便两个人的日历不留测试数据。
15. 作为维护者，我希望核对结果写进验证记录，以便之后的 epic 不必再猜云端状态。
16. 作为维护者，我希望公开的证据不含真实日期、备注、条数和房间码，以便隐私不因验证而外泄。
17. 作为已配对的房间成员，我希望首页的当日详情第一次显示就带上记录作者，以便不用等它稍后才出现。
18. 作为已配对的房间成员，我希望记录 tab 的列表一次渲染就带上「我记的 / TA 记的」，以便列表不会在眼前跳一下。
19. 作为创建了房间的成员，我希望 TA 加入后我下次打开首页看到「TA 已加入」，以便知道已经连上。
20. 作为还在等待配对的成员，我希望列表不显示记录作者，以便界面不出现没有意义的「我记的」。
21. 作为房间成员，我希望云端临时回到旧版时应用照常可用，只是暂时没有记录作者，以便回滚不会让应用报错。
22. 作为房间成员，我希望启动首屏的房间校验和设置页的房间码显示与现在一样，以便绑定和解绑流程不受影响。
23. 作为房间成员，我希望从首页切到记录 tab 时立即看到已经读到的记录，以便不用再等一次骨架屏。
24. 作为房间成员，我希望记录 tab 在后台刷新完成后自动更新，以便看到 TA 刚记的内容而不用手动刷新。
25. 作为房间成员，我希望在记录 tab 里保存后回到首页，日历上已经有这条记录，以便两个页面不出现一新一旧。
26. 作为房间成员，我希望从首页保存后切到记录 tab，列表里已经有这条记录，以便确认它确实记下了。
27. 作为记经期的房间成员，我希望打开编辑页时时长提示直接可用，以便不用等历史读取。
28. 作为补记经期的房间成员，我希望开始日落在已有经期里时仍被问「编辑那条 / 仍然新建」，以便不会不知情地记出覆盖同一天的两条。
29. 作为房间成员，我希望 TA 已经记了进行中经期时，我的新增仍被合并到那一条，以便 Room 里始终只有一条进行中经期。
30. 作为房间成员，我希望一类记录读取失败时记录 tab 的另一个分段照常显示，以便一处失败不挡住全部。
31. 作为房间成员，我希望从未读取成功的分段显示失败和重试，而不是「还没有记录」，以便不会误以为 Room 里是空的。
32. 作为房间成员，我希望曾经读到、这次刷新失败的分段保留原来的列表并给出行内重试，以便网络波动时仍能查看。
33. 作为房间成员，我希望列表已经在眼前时，后台刷新失败不弹窗打断，以便继续看手头的内容。
34. 作为刚解除绑定又加入另一个 Room 的成员，我希望看不到上一个 Room 的任何记录，以便两个 Room 的数据不混在一起。
35. 作为房间成员，我希望需要重新绑定时只被提示一次，并且由我正在看的页面提示，以便不被重复或莫名的弹窗打断。
36. 作为房间成员，我希望两个分段的下拉刷新照常可用，以便随时主动拉取最新记录。
37. 作为房间成员，我希望保存后记录 tab 仍落到被改动的分段并展开保存结果所在的月份，以便马上看到刚保存的那条。
38. 作为房间成员，我希望编辑草稿的保存、恢复和清除与现在一样，以便中途离开不丢输入。
39. 作为房间成员，我希望导出仍然在两类记录都读取成功后才写文件，以便备份不会只有一半。
40. 作为调整视觉的贡献者，我希望改一个间距、时长或色值时不用同步改测试里的字面量，以便纯视觉调整只改样式。
41. 作为调整视觉的贡献者，我希望把文字对比度降到下限以下时测试变红，以便可读性规则仍有守护。
42. 作为调整动效的贡献者，我希望去掉某个动画的减弱动效覆盖时测试变红，以便无障碍规则仍有守护。
43. 作为评审者，我希望每条保留下来的护栏断言都对应一条写明的设计规则，以便判断一次变红是违规还是测试过时。
44. 作为维护预测逻辑的贡献者，我希望里面没有无人可达的分支，以便读代码时不用推测它何时生效。
45. 作为新接手的代理，我希望每个 module 的职责只在一处维护，以便不会读到两份互相漂移的清单。
46. 作为维护者，我希望 Room 云函数的仓库源文件在下一次部署前与已部署产物保持一致，以便产物校验继续有意义。
47. 作为实现经期月份分组的贡献者，我希望记录 tab 的数据来源先确定下来，以便分组只需要基于一份记录列表来写。

## Implementation Decisions

### A. 云端列表取全

1. `list` 成功的含义定为「该 Room 该集合的全部记录」。实现用显式页大小循环读取直到取完；页大小取平台允许的单次上限（锁定的 SDK 当前为 1000，实施时复核）。
2. 排序是确定的全序：先按现有日期字段倒序，再按记录标识。结果里每个记录标识至多出现一次。
3. 任何一页读取失败，整次 `list` 失败，不返回已取到的部分。
4. 请求形状不变，旧版客户端不需要改动。
5. 进行中经期查询、单条记录查询和 Room 查询这些内部有界查询不改。
6. 接受的边界：只有记录数超过一页时才会出现第二次读取；两次读取之间另一位成员的写入可能让这一次结果多一条或少一条，下一次刷新即恢复。不为此引入快照读或游标。

### B. 配对状态随列表返回

7. dataOp 鉴权通过后，把已经读到的 Room 配对状态放进 `list` 的成功应答：字段 `roomStatus`，取值 `waiting` 或 `paired`。应答不包含成员标识、昵称或房间码。add、update、remove 的应答不变。
8. RoomDataClient 的 `list` 成功结果带上这个状态，以及本次读取所用的房间码（房间码本来就在本机）；云端没给状态或取值不认识时不带状态。RoomDataClient 仍是唯一的 records interface，ADR-0005 不变。
9. 首页和记录 tab 的配对状态只来自列表结果：有新值就采用；没有新值时沿用当前 Room 上一次的值；当前 Room 从未得到过值时按未配对呈现，不显示记录作者，也不提示「TA 已加入」。不为缺少状态的情况保留回退请求。
10. 首页与记录 tab 不再为配对状态调用 `getMyRoom`。启动首屏的房间校验、设置页的房间码与状态、stale Room 的修复路径不变。
11. 「TA 已加入」的一次性提示和配对欢迎条仍由 roomPresence 判定，输入改为列表带回的状态。

### C. 部署与真实云端核对

12. 本次只部署 dataOp，一次包含 A 和 B 的云端改动。Room 生命周期的四个云函数不部署，源文件不改。
13. 顺序：记录现状 → 部署 → 真实云端核对 → 之后才上传依赖新字段的小程序版本。客户端代码可以先合并，因为缺少新字段时的行为已由决定 9 定义。
14. 部署前记录：取回线上 dataOp 的代码，与仓库历史比对，记下对应的提交或差异；部署产物实际解析的 SDK 版本；该 Room 两类记录各自的条数；保留旧产物用于回滚。条数只记在本地，不进仓库和 issue。
15. 核对在真实小程序上下文、真实成员身份下进行，逐项记录通过、失败或未验证：
    - 两类 `list` 返回的条数与云数据库里该 Room 的计数一致。任一类超过 100 条时这一项直接证明分页；都不超过时记为「未触达分页」。
    - `list` 应答里的配对状态与实际一致，且不含成员标识。
    - 新增一条进行中经期成功；再新增一次得到同一条记录；补结束日后变为已结束；删除成功。
    - 未来日期的欢乐时光被拒绝；过去日期的新增、修改、删除成功。
    - 记录作者对当前成员正确；另一位成员一侧需要对方配合，做不到时记为未验证。
    - 导出文件里两类记录的条数与第一项一致。
    - 有已发布的线上版本时，部署后在手机上确认它仍能读取和保存；没有则记为不适用。
    - 记下 `list` 的耗时。
16. 核对用的替身记录带可辨认的备注、放在过去日期，结束时全部删除并回读确认。
17. 回滚方式是重新部署保留的旧产物。回滚后超过 100 条的截断会回来，记录作者暂时消失，其余功能不变。
18. 结果写入验证记录；README 里说明云端部署状态的段落改为新的事实。

### D. 一份共享的 Room 记录

19. 先在 ADR-0008 追加当日补充，再改代码。补充写明：共享范围从首页扩大到记录 tab 和编辑会话；记录 tab 的列表加载入口并入共享记录；决定 21 的 Room 归属规则；编辑会话保存前不再读最新列表的理由（提示是提醒，唯一性在云端）。区分标准不变：页面不持有记录副本、revision 或在途 promise。ADR 索引里 0008 的改动范围同步改写。
20. `roomRecordsSync` 从首页专属改为整个小程序共用一份：持有当前 Room 的两类记录、各集合的同步与待确认状态、在途加载和配对状态。首页、记录 tab 和编辑会话都从它读；页面在加载时订阅、卸载时退订。
21. 不变量：它持有的每条记录、同步标记、待确认状态和配对状态都属于同一个房间码。检查点有两处：采用列表结果时，以结果带回的房间码为准；加载开始和接收本地改动时，以本机当前的房间码为准。任一处发现与持有内容所属的房间码不同（包括本机已没有房间码），先清空再继续。Room leave、清除本机房间码、创建、加入和 Room 修复都落在这条规则里。
22. 已持有当前 Room 的已同步数据时，任何页面触发的加载都是静默刷新，前台还是后台由它自己判断。现有的在途加载去重、请求不超车、按集合的 revision 门、部分失败和重试文案保持不变。
23. 记录 tab 的两个分段渲染共享记录：
    - 已同步的集合直接显示，后台刷新后更新。
    - 未同步集合不显示空态：从未读取成功时显示失败和重试，本地已保存的记录照常列出；经期分段的条数和平均值显示占位。
    - 曾经同步、最近一次刷新失败的集合保留列表并显示行内重试。
    - 记录作者随同一次渲染给出。
24. 失败呈现分两层。订阅回调只更新渲染数据。弹窗、toast 和跳转只由发起这次加载的页面依据加载返回的结果执行，所以隐藏的页面不会弹出提示。可重试的读取失败在记录 tab 只用分段内的失败画面或行内重试表达，不再弹窗；未绑定和需要重新绑定仍给出「去绑定」。呈现映射仍只在 roomAccessOutcome 一处。首页的行内 Room 状态画面不变。
25. 编辑会话：
    - 时长提示和保存前的归属记录查询读共享记录里的经期，包括尚待确认的本地改动。
    - 经期已同步时，打开和保存前都不再读列表。未同步时请共享记录加载一次（与在途加载合并），结束后按当时拿到的数据继续；读不到时沿用现在的行为：没有历史就用默认时长，不出提示。
    - 保存结果未确认时的核对仍直接经 RoomDataClient 读一次最新列表，规则不变。
    - 保存和删除成功后，把记录变化交给共享记录一次，不再查找「上一个页面」转交。
26. recordPageSync 保留记录变化的构造和记录 tab 的一次性分段意图；「通知上一个页面」的适配删除。记录 tab「落到被改动的分段、展开保存结果所在月份」的行为不变，改由共享记录发布的记录变化驱动。
27. recordCommands 里绑定页面实例的列表加载入口删除，recordCommands 只剩编辑会话。
28. 设置页导出不读共享记录：仍顺序读取两类，任何一类失败即停止。

## Testing Decisions

好的测试只经公开 seam 观察外部行为：云函数的应答、渲染出的页面数据、提示、导航、本地存储和发出的云调用。不读页面私有字段，不替换应用 module，不匹配 JS 源码。本次不新增 seam，用三个已有的。

- **云端 seam：dataOp 处理器接上真实的记录逻辑和替身数据库。** 一次覆盖鉴权、取全和配对状态。替身数据库按平台行为建模：未指定条数时最多返回 100 条，指定条数时不超过单次上限。用例：250 条欢乐时光返回 250 条且标识不重复；多条记录日期相同且跨页时不重不漏；某一页读取抛错时整次失败；等待配对和已配对的 Room 分别带回对应状态；应答不含成员标识、昵称和房间码；旧请求形状照常成功。先例：room-records 和 data-op-auth 两组测试。
- **微信平台 harness：真实页面、生命周期、用户事件、可控的云应答顺序。** 用它的云调用记录断言次数，用渲染数据断言行为：
  - 首页一次显示恰好 2 次 `list`、0 次 `getMyRoom`；列表带回的状态从等待配对变为已配对后提示一次「TA 已加入」；状态缺失或取值不认识时不显示记录作者。
  - 首页读完后切到记录 tab：云应答到达之前列表已渲染，且带记录作者；应答到达后更新。
  - 从首页打开经期编辑页不发云调用；保存一条新经期只发 1 次 add；回到首页后全流程合计 3 次。
  - 开始日落在已有经期里时仍出现「编辑那条 / 仍然新建」，两种选择的结果不变。
  - 在记录 tab 保存后，首页不等自己的刷新就已包含该记录；反向同理。
  - 一类记录失败时另一分段照常显示；未同步集合不显示空态；曾同步后刷新失败时保留列表、出现行内重试且没有弹窗。
  - Room leave 后创建或加入另一个 Room：上一个 Room 的记录在首页、记录 tab 和编辑页的时长提示里都不出现，包括新 Room 有一类读取失败的情形。
  - 需要重新绑定时，只有发起加载的页面给出一次「去绑定」，隐藏的页面不弹出提示。
  - 加载途中发生本地保存时，旧快照不覆盖刚保存的记录（现有 revision 门用例继续通过）。
  - 保存结果未确认时的核对、编辑草稿、删除确认、导出要求两类都成功，这些现有用例不改断言继续通过。
  先例：home-sync、home-calendar、record-tab、record-edit-page、settings-page 测试。RoomDataClient 自己的测试只在结果形状变化处跟着更新。
- **Calendar projection 表格与周期 module 的公开函数。** 删除手动分支后，现有不带手动参数的用例结果不变；带手动参数的用例随分支一起删除。
- **护栏瘦身用变更试验验收，不设行数指标。** 改一个非不变量的值（一个间距、一个不越预算的时长、一个仍满足对比度的色值）时测试保持通过；破坏一条不变量（对比度降到下限以下、删掉一条减弱动效覆盖、加入一个裸色值、把触控目标改到下限以下）时测试变红。三组里每条保留的断言都能指到决定 29 的某一项。
- **运行态。** 记录 tab 的加载、失败、保存回流和两个编辑页，在微信开发者工具模拟器当前机型上按 UI 收尾清单过一遍。真实云端核对按决定 15 的清单执行，不由自动化替代。
- 完成前运行完整的本地验证入口；Room artifact 一致性检查必须保持通过且四份产物内容不变。

## Further Notes

- **优先级与顺序。** A、B、C 解决数据完整和线上状态不明，优先做：A 和 B 的云端部分先完成，再做 C 的部署与核对；依赖新字段的小程序版本在核对通过后才上传。D 是改动面最大的一块，可以单独推迟，不影响 A、B、C。E、F 与其他部分互不依赖，收益比前四项小。
- **需要人执行的部分。** C 的部署和真实云端核对由维护者在微信开发者工具里完成，拆票时这一张标为 `ready-for-human`；代理负责准备核对清单和记录格式。
- **与 #186 的关系。** #187 要改记录 tab 的经期分段。经期月份分组是基于一份记录列表的纯展示，两边谁先落地都可以，后落地的一方只需要调整页面接线。#188 会改动日历相关的护栏；它遇到钉位置或数值的断言时适用决定 33 的同一条规则。
- **可见的行为变化。** 记录 tab 的可重试读取失败从「弹窗加行内」变为只有行内（决定 24）。其余用户可见行为不变。
- **未核实的事实。** 云函数应答体的大小上限和线上 dataOp 的超时配置没有核实；核对时记录 `list` 的耗时，条数很大时再评估。线上 dataOp 的版本和真实记录条数在决定 14 执行前未知。
- **取证基线。** 文中的计数来自 2026-11-11 对提交 `01e3d4c` 的检索和本地运行；之后只有文档提交。
